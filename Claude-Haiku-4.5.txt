Description
This experiment evaluates an AI model’s ability to propose, implement and validate a UI/UX improvement that converts a dense, visually noisy task-list into a clearer, more readable layout. The canonical change: transform “before” dense task cards (screenshot_pre_ui.png) into “after” refreshed cards with improved spacing, hierarchy, unified buttons, consistent iconography, hover states and accessible contrast (screenshot_post_ui.png). Deliverables must include implementable front-end changes, automated visual checks that confirm the presence of specific design improvements, accessibility checks, and before/after screenshots demonstrating the effect.
Key evaluation criteria
• Faithful reproduction of the baseline “before” UI.
• Clear implementation of the improved visual language (spacing, hierarchy, unified buttons, hover states, icon consistency, whitespace).
• Automated visual and functional verification (pixel-tolerance screenshots, DOM assertions, CSS property checks).
• Accessibility checks (contrast ratios, focus states, ARIA attributes).
• Reproducible environment with one-command test/run scripts and a final compare_report.md embedding before/after images and per-check results.

Requirements for the AI Model Output
1.	Test Scenario & Description
o	Describe the scenario and what’s being tested: visual clarity, spacing, hierarchy, control affordance (buttons/hover), iconography consistency, and accessibility.
o	Define expected input/output formats for tests (JSON): test actions (load page, hover button, focus element) and expected state snapshots, e.g. {"test_id":"hover_primary","selector":".task-card .btn-primary","expected":{"background-color":"#0D47A1","box-shadow":"rgba(0,0,0,0.12) 0px 2px 8px"}}.
o	Acceptance criteria examples: primary buttons share same color and hover style; card padding ≥ 16px; title font-size increased; secondary text lighter weight; icon sizes unified; focus outline present; contrast ratio ≥ 4.5:1 for body text.
2.	Test Data Generation
o	Supply at least 5 structured test cases saved as test_data.json covering:
• Baseline visual check (load baseline page and capture screenshot).
• Card spacing & hierarchy (padding, margin, title font size, subtitle weight).
• Button consistency & hover feedback (color, hover state, pointer cursor).
• Iconography and alignment (uniform sizes, vertical alignment).
• Accessibility checks (contrast ratios, keyboard focus order, ARIA labels).
o	For each case include: test id, steps (open page, locate selector, action), expected DOM/CSS assertions, screenshot name, and pass/fail rule (exact/threshold).
3.	Reproducible Environment
o	Provide requirements.txt, setup.sh and optionally a Dockerfile to create a consistent environment. Include a lightweight static server (Flask/Node static), Playwright or Selenium, puppeteer/Playwright for visual checks, and axe-core or other a11y tool.
o	Document how to start baseline and improved apps, run tests, and where artifacts (screenshots/logs/results) are written.
4.	Test Code
o	Generate executable test code that:
a. Starts the static server hosting the UI under test.
b. Uses Playwright or Selenium to open baseline and improved pages, capture full-page and element screenshots, simulate hover/focus, and collect computed CSS values (padding, font-size, color, box-shadow).
c. Runs accessibility checks (contrast ratios, ARIA presence, keyboard focus behavior) using axe (or equivalent).
d. Compares screenshots with a tolerance-based diff and writes results_pre.json / results_post.json with per-check outcomes and measured CSS properties.
e. Reports pass/fail and writes human-readable logs (log_pre.txt, log_post.txt).
o	Tests must be runnable via provided run_tests.sh.
5.	Execution Scripts
o	Each project must include run_tests.sh to: create venv (or use Docker), start server, run tests, save screenshots and logs, then stop the server.
o	Provide a top-level run_all.sh that executes Project A tests then Project B, aggregates the result files under results/, computes diffs, and generates compare_report.md. One command should run the full workflow.
6.	Expected Output
o	For each test produce:
• results_pre.json and results_post.json — structured assertions, CSS measurements, a11y findings, screenshot file names.
• log_pre.txt and log_post.txt — test run logs and any JS console errors captured.
• Screenshots: screenshot_pre_ui.png (baseline), screenshot_pre_<testid>.png, screenshot_post_ui.png (improved), screenshot_post_<testid>.png, and optional *_diff.png showing visual diffs.
• compare_report.md — embedded thumbnails (or links) of before/after, per-test pass/fail and measured deltas (padding increase, font-size delta, contrast ratios), and an executive summary describing how the redesign improved scanability and accessibility.
7.	Documentation / Explanation
o	Include README.md explaining setup, how to run per-project tests and run_all.sh, where artifacts live, and interpretation guidance.
o	For each automated check explain what it validates and why it matters (e.g., padding/whitespace improves visual scanning; unified buttons reduce cognitive load; hover states improve affordance; contrast aids readability).
o	Call out pitfalls and limitations: pixel-perfect diffs are brittle across browsers/resolutions — use tolerance thresholds; font/render differences across OS; responsive breakpoints must be separately validated; accessibility tools flag potential but manual review needed.
o	Recommend rollout steps: A/B test with a sample of users, telemetry measuring task scan time and click success, accessibility audit by specialists, and gradual roll-out via feature flag.
